# 開発者ガイド

## 環境と起動

- Node.js LTS、npm、Windows、VS Codeを使用します。
- アプリのルートはこの文書の親フォルダーです。
- `npm install` で依存パッケージを導入し、`npm run dev` で開発サーバーを起動します。
- `npm run typecheck`、`npm run lint`、`npm test`、`npm run build` を変更確認に使用します。
- PlaywrightのChromiumブラウザーを準備した後、`npm run e2e` でE2Eテストを実行します。

## 構成

- `src/app`: ルーティング、共通レイアウト、テーマ。
- `src/data`: Zodスキーマと検証状況を含むサンプル問題。
- `src/db`: Dexieデータベースと初期化処理。
- `src/features`: 機能単位の画面。
- `src/test`: Vitest共通設定。
- `e2e`: Playwright E2Eテスト。

Phase 2の入力判定は`src/features/keyboard/engine.ts`に分離しています。回答欄にフォーカスがあるときだけキーを判定し、`key`と`code`、修飾キー集合、必要な場合の左右指定を区別します。英字は物理コードを基準とし、それ以外はコードとキー名の両方を照合します。複数段階のタイムアウトは既定1500msです。IME・リピート・フォーカス喪失を変更する際は単体テストとブラウザーテストを併せて確認してください。

`src/features/sessions`は出題とセッション画面を実装します。各回答とセッション更新は一つのIndexedDBトランザクションで保存し、採点方式・初回回答・中断理由を記録します。`outcome`と左右指定は既存データとの互換性を保つ任意フィールドです。ページを閉じる操作はブラウザーに確認を依頼しますが、プロセスの強制終了などでは非同期保存を保証できません。

Phase 3では`src/features/analytics/calculations.ts`に集計・習熟度・復習日の純粋関数を置きます。習熟度はクイズ初回キーボード回答のみを採用し、直近20件の重み付き正答率60%、目標時間に対する速度20%、直近5件の正答率20%に中立事前値を加えます。目標時間未設定、中断あり、4択・自己申告の速度は評価しません。復習間隔は1/3/7/14/30日、誤答で1日に戻し、履歴とアルゴリズム版を保持します。

IndexedDBバージョン3の移行は標準IDと衝突した独自問題を`custom-...` IDへ移し、回答・習熟度・セッションの参照を同一トランザクションで更新します。失敗時は全変更をロールバックします。旧習熟度は値を保持し、対象revisionを特定できない場合は旧データとして現行revisionの復習・適応出題から除外します。旧revisionの回答履歴は削除・再採点せず、現行revisionの回答だけで習熟度を計算します。旧履歴で`outcome`がなく`interrupted`が真のものは回答か未回答か区別できないため、採点対象から除外し履歴には残します。新規の回答・セッション・習熟度の更新は同一トランザクションで行います。

`src/features/gamification/calculations.ts` は初回正解10 XP、100 XPごとのレベル、セッション内の連続初回正解を定義します。XPは回答と同じトランザクションでセッションに加算し、累計は保存済みセッションから求めます。既存セッションや回答を変更せず、過去のXPは遡及付与しません。連続学習日数は既存の分析関数を共有します。axe-core（MPL-2.0）によるE2Eと手動確認項目は `docs/accessibility-checklist.md` を参照してください。

GitHub Pagesのサブパスに対応するため、ルーティングには`HashRouter`を使用します。配布用ビルドは相対アセットパスで生成します。

## データ変更時の注意

- 問題形式の変更時はZodスキーマ、サンプルデータ、テストを同時に更新します。
- IndexedDBのテーブル形式を変更するときは`src/db/database.ts`に新しいDexieバージョンを追加し、既存データを維持する移行を実装します。
- 標準問題はアプリ内で読み取り専用として扱います。出典未確認の項目は`pending`のままにし、架空の出典URLを追加しません。
- `src/data/standards`のカテゴリ別JSONは`npm run validate:questions`で一意性、重複、revision、出典、検証状況を検査します。ビルド前にも実行されます。既存IDを再利用せず、問題の意味を維持してrevisionを管理してください。
- 独自問題は履歴のあるIDの再利用やカテゴリ・操作名の変更を禁止し、削除は無効化します。標準IDと衝突した既存独自IDはDexieの単一トランザクション内で独自IDへ移し、関連履歴を維持します。CSVの複合列はJSON文字列です。インポートとバックアップ復元は検証後、単一トランザクションで衝突を再確認します。旧バックアップの標準・独自ID衝突も同じ規則で再割当します。
- IndexedDB version 4は既存テーブルを変更せず`deviceVerifications`を追加します。標準問題の現行revisionに対する記録を追記し、入力検出と人による対象アプリの成功確認を分離します。旧revisionは保持して集計から除外します。
- バックアップはversion 3で実機検証記録を含めて出力し、version 1・2も復元できます。検証記録のIDが既存と同じで内容が異なる場合はトランザクション全体を中止します。復元ファイルは2 MiB以下です。
- 公式出典を確認した後に限り出典URL・確認日・検証状態を更新します。実機未確認を`device_checked`にしません。
- ユーザーデータを外部送信せず、インポート実装時はZod検証と復元前確認を行います。

## 公開

`.github/workflows/pages.yml` は `workflow_dispatch` のみで、pushによる自動公開はしません。Node.js 24で `npm ci`、テスト・型チェック・lint・監査、本番サブパス検証を実行し、成功した `dist` をPagesへデプロイします。workflowはアプリをリポジトリのルートに置く前提です。別の親ディレクトリをリポジトリのルートにする場合は、GitHubが認識するルートの `.github/workflows` と各コマンドの作業ディレクトリ・artifactパスを調整する必要があります。

Viteの `base: "./"` と `HashRouter` はルートとサブパス双方に対応する構成です。`npm run e2e:pages` で実際の `dist` を `/trainer/` に配置したローカルHTTPサーバーから検証します。標準問題180問を追加後、問題データを別チャンクに分離し、初期JS約463 kB、問題データ約149 kB（gzip約8.4 kB）になりました。分析画面も別チャンクです。データチャンクは初期読み込みされます。

公開先リポジトリ名・オーナー・公開設定は未確認です。所有者の明示的な承認後にのみ、リポジトリのルート配置とworkflowを確認し、GitHubのPagesソースをGitHub Actionsに設定して承認された変更をpushし、手動でworkflowを起動します。`github-pages` 環境の保護ルールや必要な権限も管理者が確認してください。成功後に実際のURLで[テスト計画](./test-plan.md)の公開後チェックを行います。現時点ではworkflowも公開先URLも未検証です。
